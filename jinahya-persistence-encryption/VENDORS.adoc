= Provider-specific modules
:toc: macro
:toclevels: 2

toc::[]

The generic module encrypts through standard attribute converters, and both Hibernate ORM and EclipseLink are measured
against the same tests; no provider-specific code is required. Each provider module is an *extra* on top of the same
contract, built as a thin adapter over the generic module. This note records the contract they keep, what each adds,
what was decided against, and what stays open. The design was discussed with Codex before it was built.

== The contract a vendor module keeps

* The plaintext is a mapped attribute, and its column holds the ciphertext. Nothing else holds either.
* Downstream's `EntityEncryptionService` does the encryption and decryption, bytes in and bytes out.
* The bytes are the generic module's: a vendor module gets its converters from `EncryptedConverters.forType(type,
  service)`, the one public hook the generic module exposes for it, and never reaches the codecs. An attribute mapped
  one way reads what the other wrote.
* The generic module is complete on its own. A vendor module is an extra, never a requirement, and an application
  which drops it loses nothing stored.

A vendor module changes only how the mapping is declared, how the service is found, and what the provider's own paths
(DDL, cache) do with the bytes. It never touches a snapshot, a state array, a row or a backup clone, never replaces a
provider's listener, and never refuses categories of queries. The earlier integrations did exactly that, for a
listener-based design since replaced; none of it came back.

== Hibernate ORM: `jinahya-persistence-encryption-hibernate`

[cols="2,4,1",options="header"]
|===
| extra | mechanism | measured

| one annotation, `@Encrypted`, for every supported type
| a meta-annotation composing `@Type(EncryptedUserType.class)`; Hibernate ORM creates the type per attribute through
  its constructor taking the annotation and a `UserTypeCreationContext`, which gives the member, and so the declared
  java type, and the service registry
| yes: every type, an enum, a primitive

| the service by instance
| `jinahya.persistence.encryption.service` read from the `ConfigurationService` settings: an instance, a class, or a
  class name; `META-INF/services/` otherwise; a bad property fails the session factory. A class, or a class name, is
  resolved by the generic module's hook to one instance per class in the JVM, shared by every attribute and factory
| yes: one instance across two factories

| a query literal through the converter
| the type returns the generic module's converter as its `UserType.getValueConverter()`, so Hibernate ORM binds,
  extracts and renders literals through it; without it a bulk `UPDATE ... SET e.name = 'literal'` was measured to
  write the literal's own bytes into the column, a plaintext leak through the application's own query
| yes: the literal is rendered as the ciphertext's binary literal

| the declared column length, on every type
| the length of a converted column comes from its relational java type, and Hibernate ORM nulls the length of a
  temporal attribute on the standard mapping; the type's mapped java type is not temporal, so the length survives
| yes: 2048 on all 29 columns, where the standard mapping gives 255 on the ten temporal ones

| a refused mapping
| the constructor refuses `@Id`, `@EmbeddedId`, `@Version` and `@NaturalId`, from the member's own annotations, and
  fails the session factory; Hibernate ORM itself accepts `@Type` there
| yes

| ciphertext in the second-level cache
| the type's `disassemble` returns the encrypted bytes, and `assemble` decrypts; `CustomType` delegates the entity
  cache's form to them
| yes: a cache hit issues no statement and decrypts the cached form (`Cache_Test`, with Hibernate ORM's testing region
  factory)

| in-place changes of arrays and dates
| the type's `isMutable`, `deepCopy` and content `equals`
| yes
|===

A correction to the earlier note: `@TypeBinderType` was the wrong extension, as its binder receives a class, not an
attribute. The composed `@Type` needs no binder at all.

== EclipseLink: `jinahya-persistence-encryption-eclipselink`

[cols="2,4,1",options="header"]
|===
| extra | mechanism | measured

| one named converter for every supported type, nothing listed
| a native `org.eclipse.persistence.mappings.converters.Converter`, registered as `@Converter(name = "encrypted")`
  once and used as `@Convert("encrypted")` per attribute; its `initialize(mapping, session)` picks the codec from the
  mapping's attribute classification
| yes: every type, an enum, a primitive, in a unit with `exclude-unlisted-classes` and no converter listed

| correct binary DDL
| `initialize` sets the mapping's field classification to `byte[]`
| yes: every generated column is binary

| the service by instance
| the session property, an instance, a class, or a class name; `META-INF/services/` otherwise; a bad property fails on
  the first use of the unit. A class, or a class name, is one instance per class in the JVM, as on Hibernate ORM
| yes: one instance across two factories

| a refused mapping
| `initialize` refuses a mapping whose field is one of the descriptor's primary key fields, or the write-lock field of
  a `VersionLockingPolicy`, and fails the first use of the unit; EclipseLink itself accepts a converter there
| yes
|===

The column EclipseLink generates is its platform's type for `byte[]`, `LONGVARBINARY` on H2, and a length declared
on the column is not applied to it: nothing is truncated, and a value longer than the declared length is stored whole
(measured). A converter cannot see a query literal on EclipseLink, and does not need to: a bulk `UPDATE` with a
literal was measured to store the ciphertext.

Decided against, after measuring: marking the mapping mutable for arrays. EclipseLink compares a mutable attribute
with its backup clone by `equals` first, identity for an array, and then by converting both sides through the
converter, and a randomized ciphertext never compares equal, so every flush wrote the attribute. A `Date` compares by
`equals` and is fine. So the converter reports itself immutable and leaves the mapping's mutability to EclipseLink's
own `@Mutable`: declared on a `Date`, it gives copies and in-place change detection (measured); on an array it
detects the in-place change and brings the rewrite back, on every flush of the entity, a plain read included
(measured, on its own fixture: it moves the version of every transaction which loads the entity). Without `@Mutable`, EclipseLink shares one instance of an array or a `Date` between the
shared cache and every persistence context, which the README states (found by Codex's review).

== Not built, on purpose

* **An entity-aware key context on the write side** (a pre-insert or pre-update hook setting an ambient context the
  service reads the key from). The event APIs exist, but neither provider gives an exception-safe scope around the
  conversion: Hibernate ORM also converts when it populates the cache, where no entity is at hand, and EclipseLink's
  insert events can run during change calculation, with cascades in between. A lingering context could select another
  entity's key. The service sees bytes only; a tenant comes from the application's own context, and a key id travels
  in the ciphertext frame.
* **A `SessionCustomizer`** replacing standard converters with native ones: the named converter needs none.
* **A `BeanContainer` lookup** in the Hibernate module: an application which has a bean passes the instance.
* **A wider default column length in the Hibernate module.** `UserType.getDefaultSqlLength` was tried, and worked,
  until the value converter came: Hibernate ORM then sizes the column from the relational java type, `byte[]`, whose
  default is 255, and the type can say nothing. The converter closes a plaintext leak; a default length is a
  convenience. Declare a length.

== Open

. The EclipseLink converter does not survive serialization: its delegate is built in `initialize`, which EclipseLink's
  remote initialization does not call again (found by Codex's review; no ordinary path serializes it).
. Bytecode enhancement and weaving, on either module.
. Versionless optimistic locking on either type: expected to fail every update, as any randomized ciphertext does.
. Hibernate ORM's query cache, natural-id cache and cache keys: only the entity cache's form was measured.
