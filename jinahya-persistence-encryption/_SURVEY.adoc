:toc: macro
:toclevels: 3

Research date: 2026-10-14.

== Scope and result

This survey compares this module with existing Java libraries and with EclipseLink and Hibernate extension points.
Here, provider-neutral means independent of the Jakarta Persistence implementation; it does not necessarily mean
independent of Spring, a key-management vendor, or a commercial service.

* *Exact provider-neutral replacement:* none verified in this search. This is a search result, not a claim that none exists.
* *Related provider-neutral library:* jEAP Crypto provides JPA encryption converters, but does not document this module's
  paired-attribute migration mechanism.
* *EclipseLink:* transformation mappings are a promising implementation route for a plaintext Java attribute backed by
  ciphertext and legacy columns. Descriptor events are another route when retaining the two Java attributes.
* *Hibernate:* Jasypt and Crypteron provide encryption integrations, with version limitations discussed below.
  Custom types or event/interceptor integration are the routes to a purpose-built implementation.

Library features below are documented features, not independently tested behavior. Proposed mappings and integration
designs are explicitly proposals; no provider-specific prototype or compatibility test was performed for this survey.

== Baseline: what this module actually does

The comparison is based on link:README.md[the module README],
link:src/main/java/com/github/jinahya/persistence/encryption/EntityEncryptionListener.java[EntityEncryptionListener], and
link:src/main/java/com/github/jinahya/persistence/encryption/EntityEncryptionService.java[EntityEncryptionService].

[source,java]
----
@Column(name = "name", insertable = false)
private String name;

@EncryptedAttribute("name")
@Column(name = "name_enc")
private byte[] nameEnc;
----

Both attributes are persistent. The plaintext is not merely a transient convenience property.
The original plaintext column remains available for legacy rows; ciphertext occupies a separate column.

* `@PrePersist` encrypts into the ciphertext attribute. The plaintext column is excluded from the insert.
* `@PreUpdate` encrypts and nulls eligible plaintext attributes for the outgoing update.
* `@PostUpdate` restores the application's plaintext from ciphertext.
* `@PostLoad` decrypts ciphertext, or preserves legacy plaintext when ciphertext is absent.
* Migration happens on subsequent writes; untouched legacy rows remain plaintext.
* Nulling applies to nullable, nonprimitive plaintext mappings. The README explicitly describes other mappings as
  retaining their plaintext; the strongest ciphertext-only claim therefore needs those mapping conditions.
* The application supplies cryptography and entity-derived key selection through `EntityEncryptionService`.

An exact replacement would need to address both attributes, both columns, legacy fallback, migration on write,
entity-dependent key selection, and ORM lifecycle behavior. A single-column encryption converter alone is not equivalent.

The root POM currently declares EclipseLink `5.0.2` and Hibernate ORM `7.4.12.Final`.
Those are repository declarations, not versions verified against external release metadata in this survey.
Some cited API documentation describes earlier versions; compilation and behavior against the project's versions remain
to be checked before adopting an extension.

== 1. Provider-neutral libraries and approaches

=== jEAP Crypto

https://github.com/jeap-admin-ch/jeap-crypto[jEAP Crypto] is an Apache-2.0 library for application-side encryption.
Its documented features include AES-256-GCM, envelope encryption, AWS KMS and HashiCorp Vault backends, a self-describing
ciphertext container, and Spring Boot integration. The `jeap-crypto-db` module supplies JPA `AttributeConverter` helpers;
the byte-array APIs are independent of the persistence technology.

This is a relevant comparison for portable column encryption and a possible backend for `EntityEncryptionService`.
Its overview does not document pairing a legacy plaintext attribute with a separate ciphertext attribute or automatically
nulling the legacy column on migration. Standard JPA integration is evidence of a portable API choice, not proof that
the library has been tested with both providers used here.

The repository's detailed database-column document could not be fetched during this survey. Findings above are limited
to its accessible project overview; provider testing and detailed converter configuration remain unverified.

=== Standard Jakarta Persistence AttributeConverter

The https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html[Jakarta Persistence 3.2 specification]
defines conversion between an attribute value and its database representation. A typical ALE mapping is:

[source,java]
----
@Convert(converter = NameEncryptionConverter.class)
@Column(name = "name_enc")
private String name;
----

The converter would implement `AttributeConverter<String, byte[]>`, encrypting on the database path and decrypting on
the entity path. This is an architectural illustration, not a supplied converter implementation.

The conversion methods receive the value being converted, not the owning entity or an arbitrary row of sibling columns.
Consequently, a converter by itself cannot reproduce legacy-column fallback, null a separate plaintext column, or derive
a key from another entity attribute. Those behaviors need additional mapping or lifecycle logic.

For a new schema with one ciphertext column and key selection independent of sibling state, this is the simplest
portable approach to investigate. It is not a drop-in replacement for the current model.

=== Example: springcrypto-example

https://github.com/joutwate/springcrypto-example[springcrypto-example] demonstrates ALE with Spring Security crypto and
JPA `@Convert` on email and SSN attributes. It demonstrates the converter pattern, not the paired-column scheme.
Its README also demonstrates logging secrets and values; it should be treated as historical example code, not copied
as production cryptographic configuration. Its modern Jakarta compatibility was not checked.

=== Result for the exact portable scheme

No examined library documents the full combination implemented here: two persistent attributes, separate legacy and
ciphertext columns, legacy fallback, migration on write, and entity-derived key selection behind an application SPI.
Retaining this module is therefore a reasonable option when that exact model is required. This finding does not establish
uniqueness, completeness of the search, or production correctness of the current implementation.

== 2. EclipseLink-specific approaches

=== Transformation mappings: the strongest mapping-level candidate

EclipseLink's https://eclipse.dev/eclipselink/api/3.0/org/eclipse/persistence/annotations/Transformation.html[`@Transformation`]
supports transforming database columns into a Java attribute and defining a write transformer for each output column.
The https://eclipse.dev/eclipselink/documentation/2.4/jpa/extensions/a_transformation.htm[extension guide]
illustrates multiple column transformers for one attribute.

The Java extension points expose useful context:

* https://eclipse.dev/eclipselink/api/3.0/org/eclipse/persistence/mappings/transformers/AttributeTransformer.html[`AttributeTransformer`]
  receives the database record, object being built, and session, and returns the attribute value.
* https://eclipse.dev/eclipselink/api/5.0/org.eclipse.persistence.core/org/eclipse/persistence/mappings/transformers/FieldTransformerAdapter.html[`FieldTransformerAdapter`]
  can compute an output column value from the domain object, field name, and session.

*Proposed design, not tested:* map the application's `name` attribute using a transformation over `NAME` and `NAME_ENC`.

[cols="1,3",options="header"]
|===
| Operation | Proposed behavior
| Read | If `NAME_ENC` is present, decrypt it; otherwise use legacy `NAME`.
| Write ciphertext | Produce `encrypt(name)` for `NAME_ENC`, or null for absent plaintext.
| Write legacy column | Produce null for `NAME`.
|===

This could preserve the two-column storage model while removing the need to temporarily null and restore the Java
plaintext attribute. It changes the Java mapping: a separate persistent ciphertext attribute is not necessary in this
design. It also does not automatically prove that every unrelated update will trigger migration of an unchanged legacy
value; write selection and change detection need testing.

Read-side key selection must use state actually available while the object is being constructed, potentially from the
record. Do not assume every sibling Java attribute has already been populated.
Transformer service injection, null handling, randomized ciphertext, change tracking, cache hits, and merge behavior
are implementation work, not features guaranteed merely by choosing this API.

=== Descriptor events: retain the paired attributes

https://eclipse.dev/eclipselink/api/3.0/org/eclipse/persistence/descriptors/DescriptorEvent.html[`DescriptorEvent`]
exposes the entity, an associated row for certain events, and change-set information when available.
It also supplies `applyAttributeValuesIntoRow` and `updateAttributeWithObject` helpers.

*Proposed design, not tested:* register a descriptor listener, encrypt into the sibling ciphertext mapping at an
appropriate write event, arrange for the legacy column to be null in the outgoing row, and reconstruct plaintext on
the read path. This gives provider-specific access beyond portable entity callbacks.

Event timing matters: not every event has a row or change set. Updating a Java field, an outgoing row, and the tracked
state are different operations. An implementation must keep them consistent and verify behavior with weaving enabled.

No dedicated EclipseLink encryption library matching the module was verified. These are supported extension mechanisms
from which to build one, rather than a ready-made encryption facility.

== 3. Hibernate-specific libraries and approaches

=== Jasypt

https://jasypt.sourceforge.io/hibernate.html[Jasypt's official Hibernate integration documentation]
describes encrypted custom types and integrations for Hibernate 3, 4, and 5. Its page identifies version `1.9.3` and
a 2019 publication date. This is application-side encryption, but the documented type mappings do not establish support
for this module's paired-attribute migration scheme.

The separate https://github.com/phaneesh/jasypt[phaneesh/jasypt fork] contains a `jasypt-hibernate6` module.
Its existence was verified in the repository; binary compatibility, maintenance suitability, cryptographic defaults,
and support for the Hibernate 7 version declared by this project were not verified.

Do not treat either the official Hibernate 5 integration or the fork's Hibernate 6 module as a verified dependency for
this project's Hibernate 7 configuration.

=== Crypteron CipherDB

https://www.crypteron.com/docs/[Crypteron's documentation] describes an agent that encrypts `@Secure` entity properties
on persistence and decrypts them on loading, integrated with its key-management platform.
Although the overview mentions JPA, the Java download section explicitly links Hibernate 4 and Hibernate 5 agents.

It is therefore relevant as an existing ALE product, but not verified as an EclipseLink-compatible or modern
provider-neutral alternative. Neither support for this project's Hibernate version nor the exact paired-column migration
contract was established. Adoption also entails the product's account/platform model rather than only an ORM utility.

=== UserType: Java-side encryption at the JDBC boundary

Hibernate's https://docs.hibernate.org/orm/7.1/javadocs/org/hibernate/usertype/UserType.html[`UserType`]
is an extension point for a custom mapped value. A purpose-built encryption type can keep the Java representation in
plaintext while handling ciphertext when reading and binding JDBC values.

*Proposed design, not tested:* use a custom type for a single ciphertext column, with appropriate equality, copying,
and cache representation. This avoids encrypting the entity field itself solely to prepare a database write.
It does not by itself coordinate a separate legacy attribute/column or guarantee access to arbitrary sibling state.

=== CompositeUserType: multiple columns for one logical value

Hibernate's https://docs.hibernate.org/orm/7.1/javadocs/org/hibernate/usertype/CompositeUserType.html[`CompositeUserType`]
supports custom values with an embeddable mapping projection, applied using `@CompositeType` or registration.
Its persistent components need not correspond directly to fields on the application's value object.

*Proposed design, not tested:* a custom encrypted value could represent plaintext in Java and expose ciphertext,
legacy plaintext, or key metadata as mapped components. Its read construction could select ciphertext or legacy data.
This changes the domain mapping and requires deliberate conversion and lifecycle implementation.

Do not simply generate new randomized ciphertext every time Hibernate asks for a component value: stable persistence
equality, dirty checking, repeated component access, cache serialization, and merge semantics must be designed together.
The API is an enabling mechanism, not an encryption or migration implementation.

=== Interceptor and event integration: retain the paired attributes

Hibernate's https://docs.jboss.org/hibernate/orm/7.1/javadocs/org/hibernate/Interceptor.html[`Interceptor`]
documents callbacks including `onLoad`, `onPersist`, and `onFlushDirty`, with aligned property-name and state arrays.
An implementation can inspect entity context and modify persistence state. Hibernate also exposes insert, update,
and load events for more specialized integration.

*Proposed design, not tested:* locate both mapped properties, derive the encryption identifier from available entity
state, populate ciphertext, suppress outgoing legacy plaintext, and restore or preserve the application's plaintext.
This is the closer route when the existing two-attribute model must remain.

The interceptor documentation explicitly says modified flush state is propagated to the persistent object as well as
the database. An interceptor therefore does not automatically solve the current null-and-restore problem. Dirty-property
selection, snapshots, callbacks, and enhanced tracking still need coordinated handling. Changing only a transient
plaintext field also needs an explicit mechanism to make its persistent representation dirty.

=== ColumnTransformer is SQL-side, not the requested ALE mechanism

Hibernate's https://docs.hibernate.org/orm/7.1/javadocs/org/hibernate/annotations/ColumnTransformer.html[`@ColumnTransformer`]
defines SQL read and write expressions. Its documented encryption example invokes `encrypt(?)` and `decrypt(column)`
in SQL. That executes cryptography in the database and does not implement the application's Java encryption service.

EclipseLink's Java `FieldTransformer` and Hibernate's SQL `ColumnTransformer` therefore have materially different roles,
despite the similar names.

== Assessment and next investigations

For the exact portable paired-attribute contract, keep the current module as the baseline and evaluate alternatives
against its existing lifecycle tests. jEAP Crypto is more immediately relevant as a cryptographic backend or as a
single-column converter alternative than as a replacement for the migration mechanism.

For an EclipseLink-specific experiment, start with a transformation mapping if changing the Java mapping is acceptable.
Use descriptor events if retaining both Java attributes is mandatory.

For a Hibernate-specific experiment, use a custom type for a single encrypted column, investigate `CompositeUserType`
for a logical multi-column value, or investigate events/interceptors for the existing paired properties.
Existing encryption libraries need explicit version validation before consideration for this repository.

The following checks would determine whether any prototype actually improves on the current implementation:

* Insert, plaintext-only update, unrelated-field update, and explicit null assignment.
* Read-only load followed by flush: detect unintended updates or re-encryption.
* Legacy fallback and migration, including clearing the original column.
* Multiple flushes, rollback, detached merge, and optimistic locking.
* Provider enhancement/weaving and selective insert/update behavior.
* First-level and second-level cache behavior and the representation cached.
* Embeddables and secondary tables required by this module.
* Availability and stability of entity-derived key context during loading and insertion.
* Bulk operations and scalar projections: establish their behavior separately from entity lifecycle paths.

These are proposed evaluation cases, not tests executed for this survey. The module README already identifies
enhanced change tracking and shared-cache behavior as unverified for the current implementation.

== Research limits

Searches covered JPA encryption libraries and listeners, separate plaintext/ciphertext mappings, EclipseLink transformation
and descriptor APIs, Hibernate encryption libraries, and custom type/interceptor APIs.
The substantive findings above use project-maintained repositories, vendor documentation, and the Jakarta specification.
Search hits limited to unrelated frameworks, password hashing, configuration-property encryption, or general cryptography
were not treated as comparable persistence libraries.

No dependency was installed, no external library was executed, and no claim of current release support or security audit
is made. Some attempted documentation URLs were unavailable; accessible versioned references are linked instead.
Absence of a documented match in these sources does not establish absence of an implementation elsewhere.

== Verdicts and engineering estimates for this module

These are engineering judgments based on the source, documentation, and test assertions inspected for this survey.
They are not a security audit, benchmark, or report of a fresh test run.

=== Overall verdict

*The module addresses a useful, specific migration problem, but its current callback mechanism is not a general-purpose,
transparent ALE solution that I would recommend as a default for production entities.*

Its strongest contribution is the combination of a small application-facing API, provider-neutral integration, explicit
plaintext/ciphertext pairing, and legacy-data migration. The survey did not verify an off-the-shelf equivalent for that
whole contract. That is a reason to continue evaluating the design, not evidence that its lifecycle trade-offs are necessary
for every possible portable design or that the implementation is production-ready.

The decisive limitation is that the current mechanism changes persistent plaintext state to control database writes,
then changes it back for the application. That interferes with the provider's view of what has changed. Additional codec
coverage or better cryptography cannot resolve that persistence-state problem.

=== Operational and performance estimate

There is no measured throughput or latency estimate from this survey. The operation count nevertheless suggests the
dominant costs to measure first:

* Loading an encrypted entity and subsequently flushing can add an update and version advance without a business edit.
  In a read-heavy workload, database write traffic could therefore track the number of entities loaded into flushing
  persistence contexts, rather than the number deliberately modified. Batching may reduce round trips, not logical writes.
* For `k` non-null encrypted attributes, an ordinary load invokes approximately `k` service decrypt operations. If it then
  produces one update, the callback sequence adds approximately `k` encrypt operations and `k` decrypt operations for
  restoration: roughly `3k` service operations across that load/update cycle. Additional updates repeat work.
* Service operations are not necessarily remote KMS requests. A local cipher with cached envelope keys and a remote
  per-value encryption service have very different latency and cost profiles.
* Unnecessary version advances can cause optimistic-lock conflicts between transactions that would otherwise only read.
  This does not mean Hibernate or EclipseLink stop enforcing optimistic locking; it means the module creates additional
  writes and contention that violate normal read-only expectations.
* Extra updates affect transaction logs, replication, CDC, and auditing. These costs may outweigh reflection or codec
  overhead; optimize the write behavior before spending effort on micro-optimizing metadata access.

The service-call estimate follows the current listener's load, pre-update, and post-update paths. It excludes retries,
cache effects, null values, and provider-specific scheduling differences.

=== Recommended decision

Keep the encoding, mapping knowledge, encryption-service abstraction, and existing tests as assets. Treat the current
listener as a constrained integration whose limitations are part of its contract, rather than presenting encryption as
transparent to normal persistence behavior.

The first decision gate should be a small demonstrator that reads and flushes an encrypted entity without writing it,
updates plaintext exactly when requested, clears legacy plaintext during migration, and maintains coherent versions and
in-memory values across repeated flushes. Reject unsafe plaintext mappings independently of that experiment.

If the demonstrator requires provider-specific integration, choose explicitly between a shared API with provider adapters
and a narrower portable contract. The estimate for supporting both providers should follow that evidence. The absence of
an exact library match is not sufficient justification for accepting unintended writes or plaintext storage.

== Sketches: the vendor mechanisms on the basic concepts only

Only the module's basic concepts are kept here: *application-level* encryption, *per attribute (column)*, and a
*cipher suite which is provided* (by `EntityEncryptionService`). Jakarta Persistence purity is given up, at a price;
the paired attributes and the legacy migration are not assumed. Key selection is noted for each mechanism, as the
service selects keys by `getEncryptionIdentifier(entity)`.

These are *sketches from the APIs, not tested*.

=== EclipseLink: transformation mapping

One java attribute over the two columns: the legacy plaintext `NAME`, and the ciphertext `NAME_ENC`. The ciphertext has
no java attribute of its own; it exists only in the row.

[source]
----
@Transformation  String name   ──►  columns NAME (legacy plaintext) + NAME_ENC (ciphertext)

 write (INSERT / UPDATE)                         read (SELECT)
 ───────────────────────                         ─────────────
 @WriteTransformer(column = "NAME_ENC")          @ReadTransformer
   FieldTransformer.buildFieldValue(entity)        AttributeTransformer.buildAttributeValue(row, entity)
   → service.encrypt(id(entity), bytes),           NAME_ENC present? → service.decrypt(id(row), NAME_ENC)
     or NULL                                       NAME_ENC absent?  → NAME   (a legacy row)
 @WriteTransformer(column = "NAME")
   → NULL, always
----

* Two columns, as in this module: `NAME` keeps a legacy row's plaintext, read as the fallback; every write of the
  attribute nulls it and fills `NAME_ENC`, which migrates the row.
* The plaintext never reaches the row: the `NAME` write transformer always produces `NULL`, on `INSERT` and `UPDATE`.
* The entity field always holds the plaintext; it is never mutated. Dirty checking compares it with its backup clone: a
  read does not write.
* A second java attribute for `NAME_ENC` would make two writable mappings of one column, which EclipseLink rejects
  unless all but one are read-only.
* Key selection: the write side sees the whole entity; the read side sees the row and a half-built object, so the
  identifier comes from the row — the `Record` is passed as the context, and the service reads its columns.
* Price: EclipseLink-specific annotations on the entity; the transformer is instantiated by class, so the service is
  reached through a static holder or a session property.
* To check: the columns of a transformation mapping are written when the attribute is detected as changed; a legacy row
  saved after a change to another column may keep its `NAME` plaintext until `name` itself changes.

=== EclipseLink: descriptor events

[source]
----
DescriptorEventAdapter (registered per class)

 aboutToInsert / aboutToUpdate (event.getRecord())     postBuild / postClone
   row["NAME_ENC"] = encrypt(entity.name)                entity.name = decrypt(row["NAME_ENC"])
   row["NAME"]     = removed / NULL
----

* The entity is never temporarily nulled: the events edit the outgoing row, not the object.
* Key selection: the entity is seen on both sides.
* Price: event timing (which events carry a row; whether the decryption runs before or after the backup clone), the
  shared cache possibly holding the plaintext, and a per-class registration.

=== Hibernate ORM: UserType (single column)

[source]
----
@Type(EncryptedStringType.class)  String name   ──►  column NAME_ENC

 nullSafeSet(stmt, "alice", …)                 nullSafeGet(rs, …)
   stmt.setBytes(encrypt(bytes))                 decrypt(rs.getBytes()) → "alice"
----

* The entity field always holds the plaintext; Hibernate compares values through the type's `equals`, so a read does
  not write.
* Key selection: the type sees *the value only, not the entity*; `getEncryptionIdentifier(entity)` does not fit. This
  is the main price of this route: one key per type or column, or a key from outside the entity.
* Price: one type per java type, unless made generic over the codecs; Hibernate-specific `@Type` on the entity.

=== Hibernate ORM: event listeners

[source]
----
PreInsert / PreUpdateEventListener               PostLoadEventListener
  state[NAME_ENC] = encrypt(entity.name)           entity.name = decrypt(entity.nameEnc)
  (SQL uses state[]; the entity is untouched)       + loadedState[NAME] = entity.name   ← snapshot fix
----

* The entity is never temporarily nulled: the events edit the state the SQL is built from.
* Key selection: the entity is seen.
* Price: to keep reads from writing, the provider's snapshot (the `EntityEntry` loaded state) has to be fixed; that is
  Hibernate's SPI, and the riskiest part. Listeners are registered through an `Integrator`.

| reading writes | no | depends on timing | no | no, with the snapshot fix
| key from the entity (the service SPI) | write: yes; read: the row, passed as the context | yes | *no* | yes
| user's mapping | one attribute over two columns; vendor annotations | unchanged | vendor annotation | unchanged
| riskiest part | service wiring, key on read | event timing, cache | key selection | snapshot fix
|===

The common price is giving up Jakarta Persistence purity: one adapter per provider, each with its own tests. What it
buys, on all four, is the removal of the current mechanism's dominant costs: the temporary null, and reads which write.

== Current approach: the provider integrations

Of the four sketches, the two event routes were implemented: Hibernate ORM event listeners and EclipseLink descriptor
events. Both keep the paired attributes and the entity as what the keys are selected by, so the mapping
(`@EncryptedAttribute`) and the `EntityEncryptionService` are unchanged. `UserType` was rejected, as it has no
entity to select a key from; the transformation mapping, as it replaces the user's two attributes with one.

Each is a module of its own, replacing `EntityEncryptionListener`, which must not be registered alongside it:

[cols="1,2,2",options="header"]
|===
| | Hibernate ORM | EclipseLink
| module | `jinahya-persistence-encryption-hibernate` | `jinahya-persistence-encryption-eclipselink`
| entry point | `EntityEncryptionIntegrator`, found through `ServiceLoader`; does nothing without the service property |
  `EntityEncryptionSessionCustomizer`, named by `eclipselink.session.customizer`
| the service | `jinahya.persistence.encryption.service` (`EntityEncryptor.PROPERTY_ENCRYPTION_SERVICE`): an instance, its
  class, or its class name | the same
| the metamodel read | the session factory being integrated | the service's `getEntityManagerFactory()`, on the first
  event
| tests | 13, on H2 | 22, on H2: 11 with the shared cache off, 11 with it on
|===

Both work through `EntityEncryptor`, made public for this: `encrypt(Object, Snapshot)` encrypts into the entity against
the provider's snapshot, `decrypt(Object)`, and `getPlaintextAttributeNames`, `getCiphertextAttributeNames`,
`getNulledPlaintextPaths` and `clearPlaintexts` tell an engine what to rewrite.

=== The common rules

* *The entity's plaintext is never nulled.* The plaintext a nullable column must not receive is cleared only in what the
  provider builds the row from: Hibernate ORM's state array, EclipseLink's row.
* *A read never writes.* After a load, the provider's snapshot — Hibernate ORM's loaded state, EclipseLink's backup
  clone — is given copies of the decrypted plaintexts.
* *A plaintext is encrypted again only when it changed.* Against the snapshot, by its encoding, not by `equals`; or when
  its ciphertext is missing, which is a legacy row, or a new value. An unrelated change keeps the stored ciphertext.
* *A legacy row is migrated by any write of the entity*, the plaintext column nulled and the ciphertext stored; a read
  alone leaves it as it is.
* *Bean Validation sees the plaintext*, the entity never being changed under it (#9 does not arise).

=== Hibernate ORM: event listeners

[source]
----
FLUSH_ENTITY  EncryptingFlushEntityEventListener extends DefaultFlushEntityEventListener
  invokeInterceptor(event)          after the @PreUpdate callbacks and the Interceptor, once the entity is dirty
    encrypt(entity, loadedState)    ciphertexts which changed, into the entity
    values[i] = copy, cleared       the state the UPDATE is built from
    dirtyProperties += changed i    so that @DynamicUpdate writes them
  onFlushEntity(event)              restores the plaintexts, should Hibernate copy the state back (substitute)

PRE_INSERT    encrypt(entity, none); copies into the insert state, plaintexts NOT cleared
POST_LOAD     decrypt(entity); loadedState[i] = copy of the entity's
POST_UPDATE   loadedState[i] = copy of the entity's
----

* The hook point is the one an `Interceptor.onFlushDirty` has: after the dirty check, before the update is scheduled,
  the dirty properties recalculable. A `PRE_UPDATE` listener was too late: under `@DynamicUpdate` the columns written
  are already decided.
* The insert state is never cleared: for an `IDENTITY` insert, Hibernate ORM makes the state the entity's snapshot only
  after the post-insert events, so a cleared plaintext there made the first flush after every `INSERT` an `UPDATE`.
  The plaintext column is non-insertable, so the row does not carry it.
* Price: the default `FLUSH_ENTITY` listener is replaced, and the integration refuses to start over another one. The
  second-level cache entry written by an `INSERT` holds the plaintext. Bytecode-enhanced dirty tracking is untested.

=== EclipseLink: descriptor events

[source]
----
DescriptorEventAdapter, on every entity descriptor
  preInsert              encrypt(entity, none); fired while the unit of work calculates its changes
  preUpdateWithChanges   encrypt(entity, backupClone); EclipseLink calculates the changes again
  aboutToUpdate          row[plaintext field] = NULL, for every plaintext the mapping nulls
  postClone, postRefresh decrypt(clone); backup[plaintext attributes] = copies of the clone's
  postMerge              the same, only for a refresh merging the shared cache's own original into the clone
----

* `postBuild` and `postClone` of an object built straight into the unit of work are deferred until after its backup
  clone is taken; hence the backup is reset, not relied on being taken later.
* Under the shared cache, a refresh refreshes the cache's original and merges it into the clone: only `postMerge` is
  seen in the unit of work. The same event follows a merge of a detached instance, whose plaintexts are the
  application's; so only a merge whose source is the original in the parent identity map is decrypted.
* An object outside a unit of work, such as the shared cache's, is never decrypted.
* The plaintext columns of an aggregate are found through the aggregate mapping's reference descriptor, cloned by
  EclipseLink for each mapping with its fields translated by the overrides in scope.
* Price: the shared cache receives the plaintext of a new or changed entity when the transaction commits. Attribute
  change tracking, which weaving may enable, is rejected on the first event: a ciphertext set by reflection would not
  be recorded.

=== Open

* The plaintext in a provider's shared or second-level cache; the rows never hold it.
* EclipseLink attribute change tracking; Hibernate ORM bytecode enhancement.
* Sharing a `FLUSH_ENTITY` listener with an application's own.

=== The service: one context per entity

Since the integrations, `EntityEncryptionService` no longer returns an identifier for the module to pass back. Each
encryption of an instance, and each decryption of one, gets an `EntityEncryptionContext`: the service is initialized
with it once — selecting the keys from `getEntityInstance()`, preparing its cipher suite — and keeps what it prepared as
the context's attachment; then it encrypts, or decrypts, every attribute of that instance with that context.

* *Thread safety.* A context is confined to the thread of its operation, so a `Cipher` belongs in it, never in the
  service.
* *Lazy.* The service is initialized at the first attribute which needs it: an instance whose values are all `null`,
  or, under an integration, whose ciphertexts are all unchanged, never reaches it; a read which flushes initializes it
  once, for the load.
* *Where the context lives.* Inside `EntityEncryptor`: the listener and both integrations call it as before, so
  neither integration's engine changed.
